# RampPulse: переход к Rust-ядру

## Цель

Сделать один продукт с общей доменной логикой для рабочего стола и VPS. Интерфейс переводится
на React/TypeScript, Tauri отвечает за окно и интеграцию с ОС, а расчёты перрона, состояние
заявок, хранение и realtime-протокол постепенно переходят в Rust. Python и Go остаются
временными адаптерами, пока клиенты не переключены и сценарии не сверены.

## Целевая структура

```text
rust-core/       типы предметной области, переходы статусов, граф аэропорта и маршруты
rust-server/     HTTP/WebSocket, авторизация, события, SQLite, файловые вложения
src-tauri/       desktop runtime, безопасное локальное хранилище, интеграция с ОС
frontend/        React + TypeScript, карта и рабочие представления
data/            аэропорты и исходные демонстрационные данные
```

Rust-сервер должен собираться отдельно для VPS. Desktop-клиент подключается к тому же
серверу, а локальный демо-режим запускает локальный экземпляр Rust-сервиса. Клиенты не
должны иметь разные правила назначения инженера или разные переходы статусов.

## Порядок миграции

1. **Общий контракт и ядро.** В `rust-core` находятся типизированные события,
   состояния заявки и граф маршрутизации. Tauri уже подключает эту библиотеку.
2. **Rust realtime-сервис.** Добавить безопасный WebSocket с очередью записи на клиента,
   авторизацией комнат, восстановлением после reconnect и журналом событий в SQLite.
3. **Переключение интерфейсов.** Сначала операции смены и заявки, затем чат и звонки.
   На переходном этапе Python/Go можно запускать только как сравнимый эталон, но не как
   второй владелец состояния.
4. **Производительность карты.** Геометрия аэропорта строится один раз. Частые позиции
   передаются отдельными компактными дельтами; статические слои, списки и детали заявки
   обновляются только при изменении соответствующего раздела.
5. **Сборки и эксплуатация.** Один Rust-сервер для VPS, installer для Linux/macOS/Windows,
   управляемые настройки адреса сервера, логирование, миграции БД и backup.

## Формат realtime-события

Каждое сообщение имеет версию протокола, уникальный `event_id`, порядковый `sequence`,
время UTC, тип события, инициатора, ссылку на сущность и полезную нагрузку. Клиент после
переподключения запрашивает снимок, затем применяет дельты с большим sequence. Это
позволяет отбросить дубликаты и обнаружить пропуск событий.

## Измеряемые цели производительности

- Не пересобирать карту и весь DOM на каждое сетевое обновление.
- Разделить редкие изменения сущностей и частые координаты; позиции объединять до одного
  визуального кадра.
- Для рендера карты держать статическую геометрию отдельно от движущихся маркеров.
- Уменьшать объём пакета: отправлять событие сущности вместо полного снимка смены.
- Снимать CPU/RSS и размер пакета на фиксированном демонстрационном сценарии до/после.

## Текущее состояние

- Добавлен общий Rust crate `rust-core` с версионированным конвертом события,
  типизированными статусами заявок и детерминированным поиском пути по аэропортовому графу.
- Tauri подключён к ядру и сообщает версию realtime-протокола.
- Локальный desktop build теперь собирает и вкладывает Rust-сервер как собственный backend;
  Tauri запускает его на loopback, а Axum отдаёт frontend из вложенной папки. Системный Python
  и Go не требуются для нового локального runtime. Это вступает в силу после новой сборки,
  текущий установленный пакет не менялся.
- `rust-server` поднимает Axum HTTP/WebSocket сервис и использует SQLite WAL. В него
  перенесены вход/сессии, очередь допуска инженеров, заявки со статусами и блокировка ухода
  со смены при активной заявке, загрузка аэропортового JSON и предпросмотр маршрута.
- Добавлен Rust движок рабочего состояния: снимки смены для текущего интерфейса, список
  самолётов и инженеров, управление симуляцией, блокировка рёбер, перемещение специалиста,
  профиль, вылет и создание борта. Назначение выбирает свободного инженера по ETA через граф
  открытых рулёжных дорожек; обычная заявка ждёт, если лучший ETA превышает 15 минут, срочная
  получает ближайшего свободного инженера. Снимок восстанавливает поля рейса, таймера и ETA,
  которые ожидают текущие экраны. Перехват занятого инженера для ЧС, совместимость с типом
  борта и полная модель техники всё ещё требуют переноса из Go.
- Пароли и сессии хранятся с хешированием; демо-аккаунты создаются и выдаются только при
  явном `DEMO_MODE=1`. Для постепенного перехода сервер читает старые Go-сессии.
- Realtime-заявки и допуск отправляются как адресные версионированные события. На соединении
  пока есть только поток событий и транспортный heartbeat: журнал событий, восстановление
  пропущенных дельт и полный снимок смены ещё предстоит реализовать.
- На сервере уже сохраняются общий канал и личные комнаты диспетчер↔инженер, сообщения,
  отметки прочтения и непрочитанные счётчики. Whitelist содержит 16 авиационных стикеров;
  для комнаты проверяется состав участников. Сигналы WebRTC проходят адресную проверку
  участника и отправляются через realtime; сам аудиопоток должен идти peer-to-peer.
- Панель чата теперь выбирает серверный режим по feature flag `/api/meta`. В нём комнаты,
  контакты, история, текст, стикеры, статусы прочтения и сигналинг звонка идут через Rust.
  Вложения и голосовые сообщения сохраняются на сервере и в SQLite привязываются к комнате;
  загрузка ограничена 15 МБ, разрешённые MIME-типы сверяются сервером, а скачивание требует
  активную сессию и доступ к исходной комнате. Старый локальный мост остаётся запасным режимом.
- Веб-клиенты диспетчера и инженера понимают версионированные события операций и не
  перерисовывают весь экран на каждое секундное обновление симуляции. Для содержательных
  изменений пока загружается совместимый снимок состояния.
- Маршрут назначенного специалиста теперь хранится и продвигается в Rust-симуляции;
  сервер посылает компактные координаты и ETA. Диспетчерская карта двигает только нужные
  маркеры, а карта инженера правит координаты SVG без пересборки слоя аэропорта.
- Положение специалистов хранится в SQLite и поднимается после перезапуска сервиса. При
  перекрытии ребра активные пути пересчитываются; если обхода нет, клиент получает явное
  состояние недоступного маршрута. Геометрия оставшегося пути отправляется только при
  изменении очередной точки, а не в каждом секундном пакете.
- Серверное хранилище использует небольшой пул SQLite-соединений с WAL вместо одного
  глобального соединения под mutex: независимые чтения не блокируют друг друга, а SQLite
  сохраняет сериализацию транзакционных записей.
- Go/Python остаются production backend на VPS до отдельного staging перехода. Новый desktop
  runtime в этой ветке уже стартует Rust sidecar, но полный parity-аудит приложения и новую
  пользовательскую сборку ещё нужно выполнить до замены установленного пакета.

## Уже доступные Rust HTTP сценарии

- `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`
- `POST /api/auth/register`, `GET /api/registrations`, approve/reject регистрации
- `GET /api/airport`, `POST /api/routes/preview`
- `GET|POST /api/requests`, `POST /api/requests/{id}/status`
- `GET /api/state`, `POST /api/shift`, simulation/aircraft/technician controls
- `GET /api/chat/rooms`, `POST /api/chat/rooms/direct`
- `GET|POST /api/chat/rooms/{id}/messages`, `POST /api/chat/rooms/{id}/read`
- `POST /api/calls/relay`
- `GET /healthz`, `GET /api/meta`, `GET /ws`

## Следующие шаги

1. Сверить поведение нового движка смены с Go на сценариях заявок, назначения и движения
   техники; добавить перепрокладку маршрута при перекрытии РД и сохранять позицию техники.
2. Зафиксировать события в SQLite тем же sequence, что получают клиенты; добавить получение
   snapshot и replay после reconnect, идемпотентность команд и optimistic version checks.
3. Подключить существующий frontend к единому протоколу, начиная с заявок и карты; затем
   заменить полные перерисовки адресными обновлениями сущностей.
4. Подключить к серверному API вложения и голосовые сообщения; проверить звонковую машину
   состояний/WebRTC в интерфейсе и добавить STUN/TURN deployment settings. Сейчас работает
   адресный relay сигналов, аудио передаётся между клиентами.
5. Переключить VPS в отдельном staging-развёртывании, выполнить проверку восстановления БД
   и наблюдаемости, затем обновить desktop пакет и удалить Python/Go только после сверки.
